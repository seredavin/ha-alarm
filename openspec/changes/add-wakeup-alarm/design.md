## Context

Мотивация описана в proposal.md. Ограничения окружения:
- **Свет.** В спальнях есть WB-диммеры через MQTT (`light.spalnia_svet`, `light.spalnia_aleksandra_svet`, `light.spalnia_uliany_svet`, только `brightness`), торшер через `sberdevices` и розетки как `switch`. Аппаратный `transition` не гарантирован. Обновления состояния приходят эхом из MQTT с новым `Context`, а не с тем, которым вызывался сервис.
- **Колонки.** Яндекс Станции через `yandex_station` (AlexxIT). `play_media` поддерживает типы `command` (голосовая команда) и `text` (TTS). Громкость на Станции дискретная, шаг 0.1.
- **Шторы.** MQTT `cover`. Поддержка `set_position` зависит от устройства.
- **Солнце.** Есть `sun.sun` с атрибутом `elevation`. Координаты и часовой пояс заданы в HA.
- **Прод.** HA 2026.10 в Docker. Поддерживаем HA с 2025.1.

## Goals / Non-Goals

**Goals:**
- Один будильник — одна config entry. Вся логика в одном классе-контроллере, сущности — тонкие представления.
- Состояние сценария вычисляется из текущего времени, а не накапливается шагами. Тогда изменения на лету, рестарт HA и запуск «с середины» обрабатываются одинаково.
- Покрытие тестами на уровне сценариев из specs с подменой времени.

**Non-Goals:**
- Собственная Lovelace-карточка. Используются стандартные сущности, в README будет пример дашборда.
- Производственный календарь и праздники. Их можно добавить позже автоматизацией на «Пропустить следующий».
- Управление встроенными будильниками Яндекс Станции.
- Цветовая температура и цветной рассвет: в целевых диммерах их нет.

## Decisions

### 1. Структура пакета
```
custom_components/wakeup_alarm/
  __init__.py        # setup/unload entry, регистрация сервисов
  const.py           # ключи, дефолты, enum состояний
  config_flow.py     # ConfigFlow + OptionsFlow
  controller.py      # AlarmController: расписание, таймлайн, тик, вмешательство
  timeline.py        # чистые функции: next_wake(), stage_window(), brightness_at(), volume_at()
  entity.py          # базовый AlarmEntity (device_info, подписка на контроллер)
  switch.py time.py number.py button.py sensor.py
  services.yaml  strings.json  translations/{ru,en}.json
  manifest.json  icons.json
hacs.json  README.md  tests/  .github/workflows/
```
`timeline.py` не зависит от HA, поэтому его можно тестировать unit-тестами без event loop.

### 2. Хранение настроек: `Store` на запись, а не `RestoreEntity`
Значения сущностей (enabled, time, дни, числа, skip_next) хранятся в контроллере и сохраняются через `homeassistant.helpers.storage.Store` (`wakeup_alarm.<entry_id>`) с отложенной записью `async_delay_save`. Состав устройств и опции сценария лежат в `entry.options`.
- *Почему не `RestoreEntity`:* у него 14 независимых источников истины, порядок восстановления не определён, и контроллеру пришлось бы ждать, пока восстановятся все сущности, прежде чем планировать.
- *Почему не `entry.options`:* каждое изменение «на лету» вызывало бы перезагрузку записи.

### 3. Таймлайн из времени подъёма, а не цепочка таймеров
Для ближайшего срабатывания `W` вычисляются окна этапов:
- `light`: `[W − fade, W]`;
- `media`: `[W − media_lead, W]`;
- `cover`: `[W − cover_lead, W]`;
- `final`: `W`.

Старт сценария `S = min(начал окон)`. Контроллер ставит один `async_track_point_in_time` на `S`. С момента `S` до `W` работает тик (`async_track_time_interval`, 5 с). На каждом тике контроллер вычисляет желаемое состояние по `now`:
- `brightness_at(now)`;
- `volume_at(now)`;
- открыть ли шторы;

и отправляет только отличия от последнего отправленного. В момент `W` срабатывает отдельный `async_track_point_in_time`: диммируемые источники 100%, `turn_on` недиммируемых, состояние `ringing`, событие. Затем ставится таймер автостопа.
- Любое изменение параметров приводит к `reschedule()`: отменяются таймеры и всё пересчитывается. Если `now` уже внутри окна, тик стартует сразу. Так закрываются требования «на лету», «не в прошлом» и «рестарт во время рассвета».
- *Альтернатива:* цепочка `async_call_later` на каждый шаг. Сложно пересчитывать при изменениях и восстанавливать после рестарта.
- **Защита от повтора после рестарта.** Если `W` уже прошло, сценарий за этот день не запускается: `next_wake()` всегда возвращает будущее время. Перезапуск в состоянии `ringing` не восстанавливается, будильник просто становится `scheduled`. Это допустимо: свет уже горит.

### 4. Классификация источников и кривая яркости
Список источников один. Классификация выполняется в начале каждого run по текущему состоянию, а не в config flow: у MQTT-сущностей при старте HA может не быть атрибутов, к тому же устройство могут заменить.
- **Диммируемый:** домен `light`, и `supported_color_modes` содержит хоть один режим, кроме `onoff`.
- **Недиммируемый:** `switch`, `light` с `{onoff}`, а также `light` без атрибутов (недоступен). Такие сущности включаются в момент `W`, это безопасный вариант.
- Перед тиком в результат классификации добавляется флаг «уже горел»: от него зависит правило «не уменьшать».

Кривая:
`p = (now − start) / fade ∈ [0, 1]`, `brightness = max(1, round(255 · p^2.2))`. Гамма 2.2 даёт перцептивно ровный рассвет: первые минуты свет едва тлеет.
- Команда `light.turn_on` уходит, только если новое значение больше последнего отправленного и больше текущей яркости лампы. Так соблюдается правило «не уменьшать».
- `transition` передаётся (равным интервалу тика), только если лампа объявляет `LightEntityFeature.TRANSITION`.
- Команда отправляется на каждый диммируемый источник отдельно, сравнение тоже идёт по каждому источнику. Для каждого запоминается `last_set` (последняя заданная яркость) и `last_set_at`.

### 5. Громкость и медиа
- **В начале медиа-окна:**
  1. запоминается `volume_level` колонки (`saved_volume`);
  2. ставится стартовая громкость;
  3. вызывается `play_media(media_content_type, media_content_id)` из опций (по умолчанию `command` / «включи мою волну»).
- **Нарастание.** `volume_at(now)` — линейная интерполяция от стартовой громкости до максимальной на `[W − media_lead, W]`. Значение округляется до 0.01. `volume_set` отправляется только при изменении: на Станции это фактически 10 ступеней, и лишних вызовов не будет.
- **При «Стоп».** `media_stop`, если колонка в `playing`/`paused`, затем `volume_set(saved_volume)`.
- **«Отложить».** `media_pause` (Станция корректно его поддерживает), а через N минут — `volume_set(max)` и повторный `play_media`.
- *Альтернатива `media_player.turn_on` + `media_play`:* Станции не гарантируют продолжение после долгой паузы, поэтому повторный `play_media` надёжнее.

### 6. Шторы
На каждом тике в cover-окне и по событию изменения `sun.sun` проверяется `elevation >= threshold`. Если условие выполнено и шторы в этом срабатывании ещё не открывались:
- если поддерживается `CoverEntityFeature.SET_POSITION`, вызывается `cover.set_cover_position(position)`;
- иначе — `cover.open_cover`.

Флаг «уже открывали» живёт в объекте текущего запуска (run).

### 7. Обнаружение изменения освещения по семантике, а не по Context
В MQTT-окружении эхо состояния приходит с чужим `Context`, поэтому отличать «свои» изменения по `context.id` ненадёжно. Вместо этого контроллер на время run подписывается (`async_track_state_change_event`) на все источники и колонку и сравнивает новое состояние с тем, что будильник ожидает от источника.
- **Ожидание для источника:**
  - `off` — пока будильник его не включал (если источник не горел заранее);
  - `on` с яркостью ≈ `last_set` — после команды будильника;
  - `on` с исходной яркостью — для источников, которые горели заранее, пока кривая их не догнала.
- **Вмешательство:**
  - переход в `off` при ожидании `on`;
  - переход в `on` при ожидании `off`;
  - `|brightness − last_set| > 13` (≈5% от 255), если оно не объясняется последними командами.
- **Защита от эха:**
  - в течение 5 с после собственной команды на источник его обновления сравниваются с допуском по *любому* из двух последних заданных значений, а промежуточное `off`/`on` игнорируется: WB/MQTT может отдать устаревшее состояние или промежуточную яркость при `transition`;
  - сравнение яркости с допуском 13 из 255 покрывает округление процентов в WB.
- **Колонка.** Переход из `playing` в `paused`/`idle`/`off`/`standby` считается вмешательством, если будильник уже запустил воспроизведение, не ставил паузу сам («Отложить»/«Стоп»), прошло больше 15 с после `play_media`, и колонка находится не в `playing` дольше 5 с (debounce через `async_call_later`). Изменение громкости пользователем вмешательством не считается: будильник просто продолжает нарастание.
- Переход в `unavailable`/`unknown` не считается вмешательством: это сбой связи, а не человек.
- После «Стоп» любой причины подписки снимаются, и будильник больше ничего не отправляет на устройства.

### 8. Объект запуска (`AlarmRun`)
Хранит:
- `wake_at`, `scale` (1.0 или коэффициент для теста);
- `saved_volume`, `media_started`, `cover_opened`;
- по каждому источнику: тип (диммируемый или нет), `was_on`, `last_set`, `last_set_at`, история двух последних команд;
- unsubscribe-коллбеки;
- `reason`.

Создаётся в `S`, уничтожается при «Стоп». «Тест» создаёт run с `wake_at = now + duration`, где `scale = duration / max(fade, media_lead, cover_lead)`. Окна сжимаются умножением на `scale`. Тест не трогает расписание. Если во время теста наступает реальное срабатывание, тест отменяется.

### 9. Сервисы и адресация
Сервисы регистрируются один раз в `async_setup` и принимают `target` (`entity_id`/`device_id`). Записи определяются через `async_extract_referenced_entity_ids` и entity registry: `entity → config_entry_id → runtime_data`.

### 10. Сущности
- **Unique ID:** `<entry_id>_<key>`; `has_entity_name=True`; `translation_key` для имён.
- **Устройство:** одно на запись, `DeviceEntryType.SERVICE`, имя = имя будильника, чтобы карточка устройства собирала все сущности.
- **Обновление:** контроллер хранит список слушателей, сущности вызывают `async_write_ha_state` по сигналу контроллера. `DataUpdateCoordinator` не нужен: ничего не опрашивается.
- **«Состояние»:** `SensorDeviceClass.ENUM` с вариантами из спеки.
- **«Следующее срабатывание»:** `SensorDeviceClass.TIMESTAMP`.

### 11. Валидация в config flow
- Источники: `EntitySelector(domain=["light","switch"], multiple=True)`. Тип источника не проверяется (см. решение 4).
- Колонка: `EntitySelector(domain="media_player")`. Шторы: `EntitySelector(domain="cover", multiple=True)`.
- Ошибка `no_devices`, если не выбрано ни одного устройства.
- Уникальность имени — через сравнение `entry.title` среди существующих записей.
- `unique_id` записи не задаётся, иначе нельзя было бы завести два будильника на один свет.

### 12. CI и релизы
GitHub Actions:
- `hassfest` (`home-assistant/actions/hassfest`);
- `hacs/action` (category integration);
- `pytest` + `ruff`.

Версия в `manifest.json`. Релизы — git-теги `vX.Y.Z` с GitHub Release, чтобы HACS показывал версии. В `hacs.json`: `name`, `homeassistant: "2025.1.0"`, `render_readme: true`.

## Risks / Trade-offs

- [Яндекс Станция может не выполнить `play_media` типа `command`, если устройство в облачном режиме и не на локальной связи] → в README указать требование локального режима. При исключении — warning в логе, свет и шторы продолжают работать.
- [Ложная остановка из-за эха MQTT, промежуточных значений `transition` или буферизации Станции] → окно 5 с с допуском по двум последним командам, допуск по яркости 13/255, debounce Станции 5 с и грейс 15 с, опция отключения. Тесты покрывают эти случаи.
- [Диммер без атрибутов `supported_color_modes` при старте run (недоступен) будет считаться недиммируемым и включится только в `W`] → допустимо, в лог пишется warning.
- [Автоматизация пользователя (например, «Торшер Александра вместе со светом») меняет источник во время рассвета, и будильник примет это за пробуждение] → в README рекомендовать не включать в будильник источники, управляемые такими автоматизациями, или выключить опцию.
- [WB-диммер на минимальной яркости может не светить или мерцать] → нижняя граница `max(1, …)`. Если на практике потребуется, можно добавить опцию «минимальная яркость» без изменения спек.
- [Частые MQTT-команды (каждые 5 с × 3 комнаты)] → отправляются только изменения, на 15 минутах это не больше ~180 команд на лампу. Это приемлемо для WB.
- [Переход на летнее/зимнее время] → в РФ не применяется. Но `next_wake()` всё равно считает через `dt_util` и локальную timezone-aware дату, без арифметики по UTC.
- [Рестарт HA в `ringing` теряет звонящую колонку и автостоп] → допустимо. Задокументировать.
- [HACS перезаписывает локальные правки при обновлении] → правки только через репозиторий.

## Migration Plan

1. Выпустить `v0.1.0`, добавить репозиторий в HACS на проде (192.168.87.135), установить, перезапустить HA.
2. Создать три будильника: «Спальня», «Спальня Александра», «Спальня Ульяны». Источники, колонки и шторы пользователь выбирает при создании.
3. Прогнать «Тест» с `duration: 60` в каждой комнате.
4. Откат: удалить записи и интеграцию в HACS. Никакие внешние данные не меняются.
